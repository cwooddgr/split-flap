# Flip Flap audit and plan, September 2026

> **Author:** Claude Code (reviewer)
> **Date:** 2026-09-19
> **Status:** proposed-by-agent. Charlie asked for the audit ("if you were going to write this app from scratch today, what substantive changes would you make and why") and then for this write-up. He has not approved any item in it. Nothing here is decided until an item is marked otherwise.

## How this was produced

Four parallel read-only audits (tvOS app, web display and remote, Firestore backend and protocol, repo setup), followed by my own re-check of the claims that matter. Each item says how it was checked:

- **verified** means I or an audit ran a command, a query, or a script and saw the result on 2026-09-19.
- **read** means it comes from reading the code and has not been reproduced on a device or in a browser.
- **inferred** means it is reasoning from docs or code and could be wrong.

Nothing was changed during the audit except docs (the same day's cleanup of `CLAUDE.md`, `README.md`, `tvos/README.md`, and `docs/PROTOCOL.md`).

## The short version

The core design is right and I would build it the same way: one `text` field per room, layout done on each display, last write wins, a rolling 7-day `expiresAt` with a server-side TTL policy, a static web app with no build step, and the tvOS renderer (one Canvas, cached glyph halves, one coordinator) with its recorded-sample sound design.

Most of what I would change traces back to one thing. In January 2026 we chased "connection loss" on the web display and built about 300 lines of health checks, a `fetch` interceptor, and forced re-authentication, then ported it to tvOS. The cause was never the network. Part of it was missing Firestore rules (fixed at the time, commit `c3a2cd0`), and the rest is an API key restriction that blocks token refresh, which nobody found until this audit.

## Phase 0: live problems (do first, no code)

### 0.1 The web API key blocks ID-token refresh (verified)

- The "Browser key" is restricted to `firestore.googleapis.com` and `identitytoolkit.googleapis.com`. Firebase Auth refreshes ID tokens through `securetoken.googleapis.com` (Token Service API), which the key rejects.
- Monitoring, 41 days to 2026-09-19: 45 of 45 Token Service requests with the Browser key returned 403. The tvOS app's key returned 200 on 269 of 269.
- Effect: a web display's auth dies about an hour after load, and `display.js` recovers by signing out and creating a new anonymous user. `control.js` has no recovery, so a remote tab left open for more than an hour probably fails without telling anyone (inferred from the one-hour token lifetime, not reproduced).
- Fix: add the third API target to the key. `--api-target` replaces the whole list, so all three must be given:

```bash
gcloud services api-keys update \
  projects/split-flap-ff40a/locations/global/keys/0fa3a9c0-e81e-4573-8c29-f397607524f4 \
  --api-target=service=firestore.googleapis.com \
  --api-target=service=identitytoolkit.googleapis.com \
  --api-target=service=securetoken.googleapis.com
```

- Check afterwards: load the web display, leave it up for two hours, and confirm Token Service requests with that key return 200 in Monitoring and the console shows no forced re-auth.
- Risk: low. It only widens what the key may call, to an API the SDK already calls.
- **Done 2026-09-20 (decided-by-user, Charlie answered "1a").** The key now allows all three APIs. A test anonymous user refreshed its token three times with the web key and got HTTP 200 each time (it returned 403 before); the test user was deleted afterwards. The soak is still to run: leave a web display open for two hours, then check Monitoring for 200s on Token Service with this key.
- The update needed `--no-check-existing-usage`. Google refused the first attempt because the key had "active usage in the last 7 days" on eight Maps APIs. Monitoring showed what that was: 3 requests to each of the 8 Maps services in 14 days, every one a 403, on a project where no Maps API is enabled. That is the pattern of a scanner testing a key it found in a public repo, and the restriction did its job. Nothing working could break, so I skipped the check.

## Phase 1: rules (small, high value, needs a test first)

> **Status 2026-09-20:** 1.1 and 1.2 are written and tested but **not deployed**. Charlie said "ok next step" and chose to test without the emulator (no Java install). `firestore.rules` in the repo is ahead of the live rules until he runs the deploy. I chose these details myself: a 1,000-character `text` cap (the longest preset is 97 and the longest live message 94; the remote's textarea now has `maxlength="1000"`), `expiresAt` required and under 30 days with no lower bound (a lower bound would silently refuse a phone whose clock is wrong), `updatedAt is timestamp` rather than `== request.time`, and a 32-character `source`.
>
> Evidence so far: `tests/rules_test.py` passes 31 of 31 cases through Google's stateless rules-test API, and the same table fails 10 cases against the old rules, so it can tell the two apart. `tests/listener_check.mjs` (real SDK 11.0.0, real web key, production) passed its baseline under the old rules. After the deploy, `node listener_check.mjs --strict` is the live proof that a single-document listener works under `allow get`; if it fails, redeploy the previous rules from `git show 6a39f00:firestore.rules`.
>
> Found while checking live data (field names only, no message text read): 10 room documents, two of them with no `expiresAt` (one holds only `text`, one `text` and `updatedAt`), so the TTL policy will never remove those two. Nothing in our clients writes that shape. Deleted 2026-09-20 (decided-by-user, Charlie answered "2a"): `G0IPU2QL` and `MTUI30`, both created 2026-07-09 within 13 minutes of each other, the day of the tvOS 1.1 performance work, so most likely our own test writes. Every remaining room has `expiresAt`.

### 1.1 Narrow `read` to `get`

- `firestore.rules` grants `read`, which is `get` plus `list`. Our docs said `onSnapshot` needs `read`; that looks like folklore. Firebase's rules docs say `get` applies to single-document reads and `list` to queries, and production showed 4,428 GET rule evaluations and zero LIST evaluations in 41 days with listeners live (verified).
- Enumerating rooms is probably already blocked, because a query that could return an ID failing the `roomId.matches()` clause is rejected as a whole (inferred, not tested).
- Before deploying: test a single-document listener under `allow get`. The emulator needs Java, which is not installed on this Mac. The alternative is a careful live test using the recipe in the project memory (anonymous sign-up, listen, then delete the test room and the test user).

### 1.2 Validate the whole write

- Writes check only that `text` is a string of at most 10,000 characters. Other fields are unchecked, and `expiresAt` may be missing, in which case the TTL policy never removes the document.
- Proposed conditions (syntax untested): `request.resource.data.keys().hasOnly(['text','source','updatedAt','expiresAt'])`; `expiresAt is timestamp`, later than `request.time`, and within 30 days of it (30 rather than 8 because the remote uses the phone's clock); `updatedAt == request.time`; `source is string` with a short size cap; and a `text` cap near 1,000 (an 8-row board is 168 cells; check the longest entry in `quotes.json` first).
- Safe to ship: the only release writer is the web remote, which we redeploy at will. Shipped tvOS builds only read.
- Add a `@firebase/rules-unit-testing` file with the cases (room-ID regex, text cap, extra field denied, missing `expiresAt` denied, delete denied, other paths denied) and run it in CI (phase 3).

### 1.3 Billing guard and App Check

- Rules cannot rate-limit. A budget exists (Charlie's screenshot of the Budgets & alerts page, 2026-09-20): "Firebase Project split-flap-ff40a", $25 a month, alerts at 50%, 90%, and 100%, plus an account-wide "DGR Labs GCP monthly alert" at $25. Spend was $0.00. Budgets send email and do not cap spend.
- App Check: from scratch I would ship it on day one (reCAPTCHA Enterprise on web, App Attest on tvOS 15 and later per the SDK changelog). Retrofitting is limited, because enforcing it on Firestore would lock out tvOS 1.0 and 1.1 for good. If we do it, add the SDK in 1.2 unenforced, watch the metrics, and enforce only when old builds have faded.

## Phase 2: delete the resilience layer (after 0.1 has soaked)

Order matters: fix the key, run a web display for a few hours, confirm nothing needs the scaffolding, then delete.

### 2.1 Web (`display.js`, `firebase-init.js`, `control.js`)

- Remove the `window.fetch` monkeypatch, the 5-minute `getDoc` ping, the 55-minute forced refresh, and `forceReauthenticate`. The SDK refreshes tokens and reconnects listeners by itself once the key allows it.
- Replace with: render the QR code immediately (it needs only the room ID), sign in with backoff, one listener, capped backoff on listener errors, and a small status line on both pages ("Reconnecting", "Sent", "Couldn't send").
- Bugs this removes (read): auth failure leaves the display blank with no QR and no retry; a persistent listener error loops with no backoff and creates an anonymous account per pass; remote write failures only reach `console.error`; the remote's buttons do nothing until auth resolves; and the tap that enables sound also hides the QR code.

### 2.2 tvOS (`RoomViewModel.swift`), ships in 1.2

- Same deletion: health-check timer, token timer, sign-out-and-recreate. Never call `signOut`.
- Bugs this removes (read): a failed first-launch sign-in never retries and the QR code never appears (`ensureSignedIn` drops the completion on error); the 5-minute check tears down a healthy listener whenever no message arrived in the last minute and the ping came from cache, which can leave the TV deaf for up to 5 minutes after a Wi-Fi blip; and a persistent listener error loops at network speed.
- `errorMessage` and `isConnected` are published and nothing displays them. Show connectivity, from `includeMetadataChanges` snapshots or `NWPathMonitor`.
- Use a memory-only Firestore cache. The disk cache stores documents for rooms that are never opened again.

## Phase 3: one layout spec, tests, and CI

- The JS and Swift layout ports already disagree (verified by running both on the same input). On a line that needs wrapping, a double space stays a double space on web and becomes a triple space on tvOS, which can move the wrap point. Both uppercase after wrapping, so `ß` to `SS` can overflow and get cut. JS counts UTF-16 units and Swift counts graphemes, so emoji wrap differently. Swift does not split on `\r\n`.
- A parity bug already shipped once: `34c7039` fixed an infinite flip loop present since tvOS 1.0, caused by the port dropping the web's charset sanitization.
- There are no tests of any kind and no CI.
- Plan:
  1. `shared/layout-fixtures.json`: the charset plus 20 to 30 cases (`text`, `cols`, `rows`, expected rows), each at 21×6 and 21×8.
  2. Make layout a pure exported function in JS (`layoutText(text, cols, rows)`), and export `CHARSET`. In Swift, move `CHARSET` and `advanceChar` out of `BoardView.swift` (they are `private`) next to `BoardLayout`.
  3. `node --test` for JS with zero dependencies. For Swift, the cheapest route is a tiny local package holding `BoardLayout` and the charset with no Firebase dependency, so `swift test` runs in seconds with no simulator.
  4. One GitHub Actions workflow running both, plus the rules tests from 1.2.
  5. Decide the semantics once and encode them in fixtures: hard-break words longer than 21 columns (today the remainder is lost, which kills URLs), fold diacritics before the charset check (today CAFÉ shows as "CAF "), and normalize line endings.
- Delete `shared/protocol.ts` (nothing imports it) and `docs/APP_STORE_SUBMISSION.md` (a pre-launch checklist that `APP_STORE_LISTING.md` supersedes; keep its privacy-questionnaire note).

## Phase 4: web display engine and sound

- The web display still runs the architecture tvOS abandoned (read). Each of 126 tiles has its own `setTimeout` chain; every step creates and removes a DOM node and a compositor layer and allocates a fresh `AudioBuffer` of noise. The "flip" overlay shows the same glyph it covers and is visible for about 25 ms, so it is ornamental. In a background tab the timers throttle and a full cycle can take minutes.
- Rebuild around the tvOS design, staying in the DOM: four persistent faces per tile, one `requestAnimationFrame` clock advancing every tile one charset step per tick, transform-only animation, snap to target when the tab is hidden or `prefers-reduced-motion` is set, and no node creation after init.
- Sound: the hum is 126 noise bursts starting on the same instant and repeating every 100 ms, with no voice cap and no master gain (inferred from the code; the comment at the top of `SoundEffects.swift` names the same failure). Port the tvOS approach: decode the 12 clack samples once, cap voices per tick, random sample, gain, and jitter, one master gain and a compressor, driven by the central clock. Resume the `AudioContext` on `keydown` too, and show the "tap to enable sound" prompt only when the context is suspended.
- Wall-display basics: size tiles from the smaller of `vw` and `vh` with no cap (the board stops growing at 1506 px today), request a wake lock, offer fullscreen, hide the idle cursor, make the QR code bigger, and hide it after the first message.
- Supply chain: bump the Firebase JS SDK from 11.0.0 (October 2024) to 12.x, use Firestore Lite in the remote (it only writes; saves about 80 KB gzipped on a phone), and vendor a small QR generator in place of the abandoned `qrcodejs` from cdnjs.

## Phase 5: product decisions (Charlie's call)

### 5.1 Persist the room on displays

- Both displays make a new room on every launch. The tvOS app disables the idle timer so it can run for days, but after any relaunch, update, or power cut the board falls back to its default text and every phone that kept the old remote page writes into a dead room with no feedback.
- Proposal: keep the room ID (`UserDefaults` on tvOS, `localStorage` on web), resubscribe at launch so the last message returns, and add an explicit "new room" action.
- Tradeoff: anyone who scanned once keeps access until the room is rotated. That suits a home board and may not suit a shared space.

### 5.2 The display creates the room document

- Today the document does not exist until the remote's first write, and the remote does not know the board size. A 7-line message shows fully on tvOS and silently loses a line on web.
- From scratch: the display creates the document with `{v: 1, cols, rows}`, the remote reads it, previews the layout, and warns on overflow. Rules could then separate `create` (display shape) from `update` (message fields only, document must exist).
- A cheaper version needs no protocol change: put `rows` in the QR URL and have the remote import the shared layout function from phase 3 for a live preview.
- The full version cannot be retrofitted cleanly, because shipped tvOS builds never create the document.

### 5.3 Room IDs

- 6 to 8 characters from 36 symbols, 31 to 41 bits. Guessing is not a realistic threat at our traffic. From scratch: 12 characters from `crypto.getRandomValues` (web uses `Math.random` today; tvOS already uses the system generator), with the room in the URL hash only.

## Phase 7: tvOS polish, batch into 1.2

- **Audio session, 2026-09-20:** Charlie confirmed on his Apple TV that launching Flip Flap stops music. Fixed in `SoundEffects.swift` the same day: the category is set to `.ambient` before the engine starts, and the engine restarts on `AVAudioEngineConfigurationChange`. It compiles for the tvOS simulator; neither half has been checked on a device yet, and the route-change half has never been reproduced. Ships with 1.2. The original note follows.
- **Second attempt, 2026-09-20.** The first fix failed on the Apple TV: music still stopped at the first flap. DEBUG `[AUDIO]` logging showed why. Other audio was playing at app init and already stopped by the time `setupEngine` reached its `setCategory` call, which sat after the engine had been created and the players connected to `engine.mainMixerNode` and before `engine.start()`. So on tvOS something in creating or wiring the engine activates the session, under whatever category is set at that moment. The category is now set in `FlipFlapApp.init` and again in `FlipSoundPlayer.init` before the engine is created. Charlie's controls the same day: a silent app doesn't stop music, launching Flip Flap doesn't (only the first flap did), and Overflight launches without stopping music and ducks it for a callout. **Confirmed on Charlie's Apple TV the same day: music keeps playing through the flaps.** The temporary `[AUDIO]` logging was then removed. The route-change restart in the same file is still unreproduced.
- Found in the same logs: `engine.start()` took 1.5 s (08:49:04.701 to 08:49:06.238) on the main thread, inside the first tick of the first animation, in a Debug build with the debugger attached. Worth warming the engine at launch, off the first animation, in 1.2.
- Audio session (inferred from Apple's docs, not reproduced on a device): no category is set, so the app gets the default non-mixable one and launching it likely stops background Apple Music. Set `.ambient`. Nothing observes `AVAudioEngineConfigurationChange` or interruptions, so a route change (AirPods, HomePod) likely stops the engine and mutes the app until relaunch; `guard engine.isRunning` then skips every clack. Restart the engine on that notification.
- Drive the animation from elapsed time, not a sleeping `Task`: store start board, target board, and start date, and compute each tile's character in the Canvas. Slow hardware then skips steps and keeps the duration constant, the per-tick state churn goes away, and the clack sequence is known up front.
- The Canvas uses `rendersAsynchronously: true` and its closure reads `@State` through `self`. If the renderer runs off the main thread that is a data race (inferred). Snapshot the values in `body` and pass them to a static draw function, or drop the flag, which measured no effect on hardware.
- `QRCodeView` builds a new `CIContext` and regenerates the image on every body evaluation, which is every message. Generate it once.
- Swift 6 language mode and `@Observable` with the listener wrapped in an `AsyncStream`. Low value as a retrofit on its own; worth doing if 2.2 is rewriting `RoomViewModel` anyway.
- Burn-in: the idle timer is off and nothing on screen moves. Hide the QR code after the first message and consider a slight periodic shift.

## Not doing

- **Leaving Firestore.** On a blank page I would pick a Cloudflare Durable Object per room with hibernating WebSockets: it fails closed on the free plan, allows rate limiting and exact expiry, and lets tvOS drop the Firebase SDK for `URLSessionWebSocketTask`. But tvOS 1.0 and 1.1 speak Firestore for as long as they stay installed, traffic is about eight messages a day at no cost, and phases 0 to 2 remove the risk without a rewrite. Supabase (free projects pause after a week idle) and CloudKit (public-database writes need an iCloud sign-in, so a guest's Android phone could not post) are out.
- **Metal, SpriteKit, or CALayer for the tvOS board.** After the glyph cache the A10X settled 8 of 8 cycles in 4.4 to 4.6 s with zero stalls. No measurement justifies it.
- **A build step for the web app.** Nothing in this plan needs one.
- **XcodeGen.** The project uses synchronized groups and the pbxproj has changed in only 9 commits. Optional, for consistency with our other projects.
